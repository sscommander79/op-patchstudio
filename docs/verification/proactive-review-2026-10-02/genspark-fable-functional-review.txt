## Material findings

### F-1 — Root cause identified for OPEN defect HV-001: drum Table actions column is 72 px too narrow for its fixed-width buttons
- **Status:** Known open defect (HV-001); the **cause diagnosis is new** — human-issues.md records "screenshot establishes the visible defect, not its CSS cause."
- **Severity:** medium (presentation defect on every loaded Table row). **Confidence:** high (arithmetic from source; not browser-reproduced in this read-only pass).
- **Where:** `src/components/drum/DrumSampleTable.tsx:529` and `:575` — `gridTemplateColumns: '120px minmax(200px, 1fr) minmax(200px, 1fr) 180px'`; actions cell `:757–799` renders **five** `IconButton`s; `src/components/common/IconButton.tsx:18–23` hard-fixes each at 44 px (`min/maxWidth`, `flexShrink: 0`).
- **Trigger → consequence:** Any loaded row renders 5×44 px buttons + 4×4 px gaps + 16 px `paddingRight` = **252 px** inside a **180 px** grid track. With `justifyContent: 'center'` the overflow spills symmetrically: ~36 px leftward into the waveform column (overlapping the Play area — exactly the user screenshot), and ~36 px rightward where the row container's `overflow: 'hidden'` (`:548`) clips the rightmost control. The column presumably fit when rows had 3 buttons (3×44+8+16 = 156 ≤ 180); adding Record and Slice buttons broke it silently.
- **Adjacent:** the mobile card header (`:355–393`) has the same 236 px fixed icon strip beside a shrinkable name in a no-wrap flex row; on ~375 px viewports the icons can overflow the card. Not user-reported; check during the same repair.
- **Remediation direction:** widen the track (`minmax(252px, max-content)` or `auto`) or allow wrap in the actions cell; update the header grid to match; then the HV-001 human retest per human-issues.md.
- **Test coverage:** component-map.md shows `DrumSampleTable.tsx` has **0/0 unit-executed functions**; the 12-baseline visual contract passed repeatedly while this defect exists, so current baselines don't assert this geometry. **Missing regression:** a bounding-box containment assertion (actions cell fits its grid track; no sibling-column intersection) at the failing and nearby widths, per the retest plan already written in human-issues.md.

### F-2 — HV-004 Safari Overview overflow: concrete CSS hypothesis (cause still unproven)
- **Status:** Known open defect; this is a **new hypothesis**, explicitly not proof.
- **Severity:** medium (matches existing triage). **Confidence:** low-medium — consistent with Safari's known percent-height-SVG-in-fr-grid-row sizing bugs, but unverified against real Safari.
- **Where:** `src/styles/studio.css:392` (`.studio-launch-module { grid-template-rows: auto minmax(112px, 1fr) auto; }`) + `:397` (`.studio-launch-diagram { height: 100%; min-height: 112px; overflow: visible; }`) + `src/components/common/StudioShell.tsx:52/62/74/88` (`preserveAspectRatio="none"`, viewBox 280×112).
- **Trigger → inferred consequence:** `height: 100%` against a `1fr` row is resolution-order-sensitive; Safari historically falls back to the replaced element's intrinsic ratio (112/280 of the rendered width). On wide launch cards that yields an SVG much taller than the row, and `overflow: visible` lets it paint over the footer/labels — matching the screenshot (artwork extending into card footers, External Gear strip overlapping). The OP-1 Field selection in the screenshot is plausibly orthogonal (both appearance arts share the same classes, `OpxyLaunchArt.tsx:11–78`).
- **Remediation direction:** give the diagram a definite height (`aspect-ratio: 280/112` + `height: auto`, or a fixed row height) and change `overflow: visible` to `hidden`; then reproduce/verify in real Safari per the HV-004 retest plan.
- **Missing regression:** a WebKit Playwright geometry check (diagram bbox ⊆ module bbox; footer not intersected). Playwright-WebKit is not Safari, but it is the best computer-verifiable proxy before the mandatory human Safari retest.

### F-3 — Legacy external-drop filters silently reject AIFF/FLAC without MIME types — currently dead code, but a data-loss trap if ever re-enabled
- **New observation.** **Severity:** low (paths are presently unreachable). **Confidence:** high on the source analysis; medium on "unreachable in all browsers."
- **Where:** `src/components/drum/DrumSampleTable.tsx:131–143` and `:169–171`; `src/components/drum/DrumKeyboardContainer.tsx:403–405` and `:485–487` — filters accept only `file.type.startsWith('audio/') || name.endsWith('.wav')`, excluding `.aif/.aiff/.flac/.m4a/.ogg` files that arrive with an empty MIME type (common for AIFF on some configurations), while `DrumTool.handleFileUpload` (`DrumTool.tsx:109–116`) and `AUDIO_FILE_ACCEPT` (`audioFormats.ts:17`) accept all of them.
- **Why currently dormant:** `AudioImportProvider.tsx:59` installs a **document-capture** `drop` listener that intercepts every external drop on `[data-audio-import]` elements and calls `stopImmediatePropagation()`, so React's bubble-phase `onDrop` handlers never fire for external files; internal sample drags (typed `INTERNAL_SAMPLE_DRAG_TYPE`, `externalFileIntake.ts:19`) deliberately pass through to the swap logic.
- **Consequence if the provider is removed/unmounted or the capture listener fails:** supported-format files are silently dropped (no notification), i.e., latent supported-format data loss.
- **Remediation direction:** delete the legacy per-component file-drop filtering (keep internal drag/swap handling), or align the filter with `AUDIO_FILE_ACCEPT`. **Test gap:** no test pins "external drops on drum rows route through AudioImportProvider, not the legacy filter."

### F-4 — Keyboard Undo/Redo is not gated by Project-toolbar busy states; safety currently rests entirely on identity guards
- **New observation; defensively mitigated — robustness note, not a proven data-loss bug.** **Severity:** low. **Confidence:** high.
- **Where:** `src/components/common/ProjectKeyboardShortcuts.tsx:8–18` dispatches UNDO/REDO whenever no modal/editable target is active; `ProjectToolbar.tsx:119–120` disables the equivalent buttons whenever `busy !== null` (download/open/library).
- **Trigger → consequence:** Cmd+Z while "Open project" is decoding mutates edit identity; `openProject`'s `projectEditIdentityMatches` check (`ProjectToolbar.tsx:60–62`) then correctly fails the import with "Your current project was kept" — safe, but the user's intentional import is aborted by a shortcut the equivalent button forbids. Same asymmetry during library save (snapshot taken synchronously, so no corruption).
- **Remediation direction:** either expose busy state to the shortcut handler or accept and document the asymmetry; a unit test asserting the identity-guard failure path under mid-import UNDO would convert the mitigation from incidental to guaranteed.

### F-5 — SessionRestorationModal is a hand-rolled dialog outside the owned-dialog system
- **New observation.** **Severity:** low (works; a11y-debt adjacent to the recorded backlog). **Confidence:** high.
- **Where:** `src/components/common/SessionRestorationModal.tsx:44–73` — bespoke two-button focus trap; Escape is swallowed (`preventDefault`, no action — plausibly intentional to force an explicit restore/discard choice); it does not register with `useOwnedDialog`'s `dialogStack` (`useOwnedDialog.ts:4`), so if any other owned dialog ever coexisted, Escape/trap ownership would conflict. Today it renders before other dialogs can open, so no live conflict.
- **Remediation direction:** migrate to `useOwnedDialog`/`AccessibleDialog` when touching this file; keep Escape-as-no-op explicit and commented. Existing coverage: `sessionRecovery.test.tsx:50` exercises discard; no test asserts trap/Escape semantics.

### F-6 — Library preview error message conflates failure modes
- **New, minor.** **Severity:** low. **Confidence:** high. `LibraryPage.tsx:76–78` catches every `previewSummary` failure (missing preset, unsupported type, decode error, playback error) and always reports "saved preset is no longer available", which misdirects retry behavior for decode/playback failures. Direction: branch the message on the thrown error. No test asserts the distinct messages.

### F-7 — Capture-session queued-message replay can interleave with newly arriving port messages
- **New, theoretical.** **Severity:** low. **Confidence:** low (ordering-window analysis only).
- **Where:** `src/audio/recording/captureSession.ts:150–165` — during `enableInput`, early processor messages are buffered, the live handler is swapped in at `:160`, then the buffer is replayed with `await`s (`:162–165`). A message arriving between the swap and a replay `await` is processed before older buffered messages. For `format`→`take` or `stopped` orderings this is benign in current `handleMessage` logic, but it is an invariant held by accident. Direction: replay the buffer before swapping the live handler, or route live messages through the same queue until drained. HV-005's extensive channel/startup tests don't cover this interleaving.
