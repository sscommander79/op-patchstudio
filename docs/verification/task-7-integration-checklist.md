## Scope and precedence

- Keep ordinary file chooser, directory chooser where supported, external file/folder drop, existing OP-1 drum preset import and patch.json settings import reachable.
- The current Task 7 brief takes precedence over the older import notes on ambiguous filenames: ambiguous/unknown suggestions remain **unassigned** until the user chooses an assignment. The older proposal to fill arbitrary remaining pads automatically is not the default for suggestion review.
- This rule applies to optional filename-suggestion review. An explicit import-to-chosen-pad remains explicit destination intent, and a traditional general batch may follow its chosen intake plan for free pads. Neither route authorizes overwriting an occupied pad implicitly. The controller confirmed this interpretation; no additional permission decision is needed.

## Shared intake operation

Use a small explicit pipeline: **capture handles → resolve ordered files → validate/decode → review proposals → guarded Apply**. A useful result shape contains stable intake IDs and ordered `accepted`, `rejected`, and `unresolved` records, each with source/path context and a reason. These names describe the contract, not required new module names.

- [ ] During the synchronous drop handler, capture FileList values, file-kind item handles, available entry handles and any file-system-handle promises. Do not retain a DataTransfer object for later access after an await. Isolate one item's synchronous capture failure so valid siblings still proceed.
- [ ] Choose a complete available file channel instead of concatenating duplicate DataTransfer views. Use fallback files for unresolved channels when association is known; where two files might be distinct, preserve them and explain ambiguity instead of deleting one.
- [ ] An intake ID belongs to the item/object, not its basename, size, timestamp or directory-relative name. Include same-name/same-size/same-time/different-content fixtures. Preserve original File objects and relative paths for display; do not derive file identity or archive entry paths from names.
- [ ] Traverse directories until the reader returns an empty batch. Bound depth, encountered entries, total accepted File bytes, concurrent directory reads and concurrent decodes. Preserve top-level input order and a documented deterministic child order independently of promise completion. Report when limits stop traversal; never classify a failed directory as a successful empty folder.
- [ ] Keep valid siblings when an entry or directory fails. Progress reports distinguish discovered, preparing, accepted, rejected and capacity-excess counts. Unsupported, inaccessible, zero-byte and undecodable files each get a visible reason; a directory-level error need not invent its unknown child count.
- [ ] Distinguish internal move/assignment drags using the application's explicit internal drag ownership/payload. Internal moves keep move indicators; external imports use copy behavior. One drop must not both reorder an existing sample and start external imports.
- [ ] Plain file paths, URI lists and text-only drags do not supply local bytes. Offer the ordinary chooser fallback. Do not fetch their arbitrary URLs, infer local filesystem access or claim that a Splice drag was imported when no usable File was captured.
- [ ] A visible operation Cancel invalidates its generation immediately, stops scheduling work and discards late results. File reads, entry callbacks and decode may finish later; check generation after every await and before review updates. They cannot reopen canceled review or dispatch into a replacement project.
- [ ] Device/project replacement and a second intake operation need an explicit ownership policy. Keep independent operation IDs if deliberately allowing both, or cancel the superseded operation. Do not let shared `SET_LOADING(false)` from one file hide another active operation.

## Content, metadata and identity

`audioFormats.ts` currently dispatches only WAV, AIFF and MP3 readers; M4A/OGG/FLAC are advertised and recognized by extension but fall into an unsupported-reader branch. MP3 currently invents 16-bit source depth from decoded PCM, and the WAV wrapper sets `isFloat:false`. These are concrete integration points for Task 7's truthful metadata requirement.

- [ ] Centralize the advertised candidate format set and inspect signatures/container markers before selecting a reader. Missing MIME must not reject a valid signature. An extension alone must not certify content; an audio MIME alone must not bypass validation.
- [ ] Retain dedicated WAV/AIFF metadata where verified. For browser-decodable compressed formats, lack of a dedicated metadata parser must not by itself reject successful decoding. Distinguish verified source metadata from decoded buffer dimensions and unsupported/unknown fields.
- [ ] Represent unknown compressed-source bit depth honestly through the relevant type/serializer/UI path. Decoded Float32 storage is not evidence that the original MP3 had a 32- or 16-bit PCM source. Do not use a fabricated value just to satisfy `AudioMetadata.bitDepth:number` or a “keep original” export option. Preserve explicit configured conversion settings; the Task 5 fix must not be undone by source-dependent automatic rewrites.
- [ ] Preserve original file bytes, actual MIME/signature interpretation, original name and available source rate/channels separately from browser-decoded rate/channels. Keep decoded AudioBuffers immutable. Use existing lossless serialization; do not re-encode every original into a lossy “source”.
- [ ] Enforce File/count and known decoded-dimension limits before costly work. For compressed formats where an exact decoded size cannot be established before browser decode, document that boundary, bound input/concurrency, validate immediately after decode, and do not claim a pre-decode guarantee the implementation cannot enforce.
- [ ] Browser import support and OP-XY export support are separate. A browser-decoded compressed source still exports through the accepted WAV/AIFF conversion path. Actual output bytes and metadata must agree, including user-selected resampling.

## Filename proposal and partial-failure UX

- [ ] Suggestions are optional, deterministic proposals with a visible reason such as “filename contains kick”; do not describe filename matching as measured sound recognition. Additional audio features are optional and require their own bounded/tested meaning.
- [ ] Match whole tokens/common abbreviations with explicit precedence. Current physical labels support kick 0/1, snare 2/3, clap 5, closed hi-hat 8, open hi-hat 10, and tom slots 12/14/16/19. Distinguish open/closed hats before generic hat; avoid broad substring matches that misclassify unrelated names. Generic percussion and conflicting tokens require clear ambiguity handling.
- [ ] Reserve proposed matching slots in review order, considering already occupied pads and other proposals. Unknown/ambiguous items remain unassigned by default. A user can edit each destination or keep it unassigned; duplicate filenames and excess files stay distinct and visible.
- [ ] Show accepted files alongside rejected/unresolved reasons. Let the user explicitly Apply the accepted selection; one failed file must not discard valid siblings or be reported as a successful load. Cancel before Apply leaves the complete project unchanged.
- [ ] After review, freeze selected IDs/names/destinations during preparation or invalidate preparation on edits. Stable row keys use intake IDs, not editable names or sorted positions. Preserve unapplied/rejected/capacity-excess items until the user removes them or closes review under the stated policy.
- [ ] At commit, revalidate current occupancy, source identity for replacements, aggregate admission and explicit consent against the real incoming reducer state. If a target changed, refresh its decision rather than transferring permission to a different sample. Receipt counts reflect actual committed assignments/overflow, never proposed counts.
- [ ] Only a successful matching receipt removes applied items from review. One accepted batch is one Undo; a canceled/rejected/no-op operation creates no musical history. Multisample excess stays in review under the accepted Task 6 model; do not invent unassigned multisamples.

## Reuse accepted Task 5 accounting; await accepted Task 6 commit

- `SLICE_LIMITS` documents accepted source and project ceilings; `storedZipStructureBytes` and the maximum **63,100-byte ZIP reserve** cover the exporter's fixed 513-entry layout in addition to its full 2 MiB manifest reserve.
- `planSliceApplication` already counts both-workspace inventory when supplied, each logical opfloat header, ordinary retained source Files and omitted derived source copies. Reuse/extract its **project-accounting rule** through the accepted Task 6 helper. Do not call it with dummy slice ranges to validate arbitrary imports: imported originals and recorded takes have different representation/retention semantics from derived slices.
- Portable decoded admission is `sum(24 + 4*C*F)` per logical reference, at most 128 MiB across both workspaces. Count at most 256 loaded references, including drum unassigned assets. Stored admission includes actual source representations plus manifest and ZIP allowances; identity deduplication assumptions must match the exporter.
- Preserve source bytes once where required; derived slices already omit duplicate source payloads. Imported files should not acquire fictitious `sliceProvenance` merely to reduce storage estimates.
- `COMMIT_PREPARED_SLICES` establishes the accepted pattern: current-state planning, local all-or-error reduction, postcondition checks and an operation-ID receipt. Its name/payload is slicing-specific. **Await accepted Task 6's reusable guarded Apply API before implementing Task 7 dispatch**, then adapt file intake to that tested boundary. Preparation may run asynchronously; final validation/commit must not await. Ordinary `BATCH_EDIT` alone does not detect silently rejected child actions.

## patch.json boundary and preservation

- [ ] Before hydration or merging, require a bounded plain top-level object with the expected `drum`/`multisampler` type. Validate known nested objects, playmode/enums, finite numbers/ranges, envelope shape/ADSR values and scalar types. Include `1e400`, arrays, null and wrong-type engine/envelope fixtures.
- [ ] Reject prototype-mutating keys recursively before any deep merge. Preserve safe unknown fields and exact untouched raw values in the immutable imported JSON. Do not mutate or normalize that preserved raw document to match UI percentages; separately derive editable settings with the accepted conversion rules.
- [ ] Bound JSON bytes, depth, key/array counts and the resulting whole-project manifest, including already retained imported settings from the other mode. A nominally acceptable file must not create a project that exceeds the 2 MiB combined manifest limit.
- [ ] Malformed input or canceled reads leave settings, audio, raw imported JSON and history unchanged. A valid settings import hydrates and preserves its raw object as one musical action, retaining the accepted Task 4 explicit-replacement versus ordinary-addition policy for imported crossfades.
- [ ] Never execute/fetch imported values. Preserve OP-1 preset and ordinary patch import entry points without routing them through filename drum suggestions accidentally.
