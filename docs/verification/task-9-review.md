### R9-3 — P1: One tab's update reloads another tab which chose Later

**Anchor:** `src/components/common/PWAUpdatePrompt.tsx:8–13`, with update/defer handlers at `:26–30`.

The component calls `registerSW` without `onNeedReload` or any per-tab consent gate. The installed `vite-plugin-pwa` adapter (`node_modules/vite-plugin-pwa/dist/client/build/register.js`, `showSkipWaitingPrompt`) installs a `controlling` listener when a waiting update is observed; on `event.isUpdate`, it calls `window.location.reload()` unless an `onNeedReload` callback was supplied. Hiding the component notice with Later does not remove this listener. Thus an Update now action in tab A can allow the same waiting worker to take control of tab B, whose listener may reload its editor despite B having deferred, losing a modal-local waveform draft or interrupting recording.

The controller has been asked to verify two production tabs sharing an origin: B opens/edits a waveform draft and chooses Later; A activates B-build; assert B did not navigate, lose its draft, or interrupt active work. The controller subsequently reproduced this behavior in production; see the confirmed A/B addendum below. This is **P1** because explicit update deferral discards unsaved work. Add per-tab explicit reload consent and coverage for external activation; ensure an old open tab can continue to obtain its required lazy assets after another tab updates.

### R9-4 — P1: Stop failed MIDI auto-initialization from continuously replacing drum pads

**Anchors:** `src/components/drum/DrumKeyboardContainer.tsx:58–63`; `src/hooks/useWebMidi.ts:47–86`; `src/components/drum/DrumKeyboard.tsx:320–345`, rendered at the keyboard's `OPXYKey` call sites.

`DrumKeyboardContainer` automatically calls `initialize()` whenever MIDI is not initialized and is not currently connecting. It does not check support, a previous failure, or a one-attempt marker. `initialize()` sets `isConnecting=true`, awaits WebMidi enablement, then restores `isConnecting=false` and records an error when access fails. If the asynchronous permission failure occurs after the connecting state is rendered, the parent effect runs again and immediately retries. A denied or repeatedly failing MIDI permission can therefore cause a continuous parent-render cycle. The same auto-initialization policy also exists in `VirtualMidiKeyboard.tsx:69–73` and should receive consistent failure ownership.

Inside DrumKeyboard, `OPXYKey` is declared as a new component function on each render. React consequently replaces each pad subtree when the parent renders, even if its key and selected state did not change. This converts MIDI error-state churn into continuously detached pointer targets. The controller's first-click production log reports detachment while waiting for visibility/stability, before the click is dispatched; it does not support mouseleave/pressed-key handling as the original cause of that cold-page failure. Mouse and keyboard pressed-state updates can independently replace those inline pad components after activation and threaten focus/keyup ownership.

The retry policy and inline component seam predate Task 9; they are newly exposed acceptance blockers on the upgraded dependency/browser matrix, not proof that Task 9 introduced those source lines. The WebMidi lock changed from 3.1.12 to 3.1.16. Current installed WebMidi code directly awaits `navigator.requestMIDIAccess` (`node_modules/webmidi/dist/esm/webmidi.esm.js:11930–11944`). The controller is collecting request-attempt/rejection or equivalent browser evidence to confirm the continuous-render trigger; source inspection establishes the retry path and unstable React component identity, while the matrix and offline logs establish actual user-facing detachment. Immediate unsupported failures may be batched differently, so do not infer that every browser must exhibit the same loop.

Bound automatic initialization to one supported attempt; retain a meaningful error and explicit user retry instead of retriggering from the false connecting state. Hoist the pad component (or render it without a new component identity) and pass its state/handlers explicitly so parent state changes preserve actual button nodes. Verify denied/unsupported MIDI with stable pad identity, pointer selection/audition, keyboard focus and keyup cleanup. Do not resolve these failures by forced clicks, sleeps, greater timeouts or dropping the real pad interaction from tests.

**Evidence status:** actual browser detachment established by controller logs; causal source chain established; request-frequency instrumentation remains controller-owned. This finding blocks Task 9's retained interaction/browser/offline requirements even though the relevant inherited source was accepted earlier.
