**Findings**

- **Medium** `src/audio/recording/captureProcessor.ts:42`, `src/audio/recording/captureProcessor.ts:47-57`: `failed` does not terminate processing. If initial `CaptureCore` construction rejects an unsupported delivered layout, each later callback retries construction and emits another error. After the no-input timeout, a later valid block can initialize the core and emit `format` or capture data after the fatal error. Short-circuit `process()` when `failed` is set, while continuing to zero outputs. Extend `src/test/audio/recording/captureProcessor.test.ts:58-69` with subsequent callbacks asserting one error and no later format/take.

- **Medium** `src/audio/recording/captureSession.ts:127`: when `sampleRate` is omitted, capacity is reserved at 48 kHz even though the subsequently created context may run at 96 kHz. A stereo 96 kHz capture can therefore require approximately twice the preflight reservation and exceed `RECORDING_LIMITS.ownedBytes`. Reserve against the actual context rate after creation, or conservatively reserve at the supported 96 kHz maximum. `src/test/audio/recording/captureSession.test.ts:27-36` only covers reported 48 kHz.

- **Medium** `src/audio/recording/captureSession.ts:159-162`: processor messages queued during `context.resume()` are dispatched without awaiting them, and `enableInput()` then unconditionally returns `true`. First-frame initialization errors introduced by this change can therefore transition the session to `error` and begin asynchronous teardown while the setup call reports success and proceeds to enumerate devices. Drain startup messages in order and return `false` if one invalidates the generation or fails the session. Add coverage for queued processor `error` and unsupported `format` messages during resume.
